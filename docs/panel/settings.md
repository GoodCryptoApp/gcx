# Settings

Settings has three tabs along the top, as the Trade page does: **General**, **Exchanges** and **Alerts**; it opens on General. General is one page with three separate titled cards, in order: Installation, Preferences, and About goodcryptoX. A chevron opens a page; that page has its own title in the header and no tabs, and the header's back button returns to the page you came from. Settings rows use one faint divider between rows, with no extra line above the first or below the last.

## The roadmap banner

Under the tabs, on General only, a green-tinted band: **What's next for goodcryptoX**, *See the roadmap and vote on what we build next*, and a **See the roadmap** button (green words on a faint green tint) that opens goodcryptoX's voting roadmap on the website in a new tab. Where the window is too narrow for the line and the button side by side, the button moves under the line and reads **Vote now**. The cross at the right closes the banner for good in this browser; the roadmap stays one press away in About goodcryptoX.

## Installation

The first row shows the three-part version and build number, the actual running tier and, where recorded, the day this build was installed: **Version 3.0.0 (13613) · Updated 18 Oct**. The build number is small and grey. A Beta copy adds its tier word. Its right side says **Running**, or names an available update with an **Update** button: **Update available: 3.1.0**, or, when only the build differs, **Update available: 3.0.0 (11843)**. On a server the row reads the same way: **Running** while nothing is newer, **Update** when a newer build is known; the updater beside goodcryptoX installs it.

- **Start goodcryptoX when I log in**: the system's own answer (the Mac's and Windows' helper's, the user service's on Linux), also refreshed when General is reopened or the browser tab becomes visible. An external change in the system's own list (System Settings on a Mac, Windows Settings › Apps › Startup on Windows, `systemctl --user` in a terminal on Linux) therefore updates the switch; when the system keeps it off, the line says where to allow it, by that system's own names. Docker has no login row.
- **Keep the Mac awake** (**Keep the computer awake** on Windows and a Linux desktop): on mains power, held throughout the goodcryptoX run, even with no connected account; on battery or unknown power, while goodcryptoX has something to trade on: an order resting or on its way, a stop it fires itself or the exchange holds, an order placed elsewhere resting on a connected account, a bot whose entry, averaging orders or timer is due, a TA bot waiting for its signal. A bot waiting for its start, a webhook or the end of its cooldown, and an order waiting for its start time, let the computer sleep; they act when it wakes. Power is checked once a minute. The row's tooltip, on or off, says “Keeps the computer awake so goodcryptoX can watch your bots and orders”; there is no line under the row. Turning it off asks once, and the question says that goodcryptoX cannot react to fills, place take-profits/stop-losses or run bots while asleep; **Keep on** cancels without changing the setting. Docker has no awake row. Closing the computer's lid can still put it to sleep.
- **Storage** (under the first row, with the folder's total at the right) opens the page [Storage](#storage).
- **Reports to goodcryptoX** is beside Storage, before Move or remove; its privacy link opens the built-in policy.
- **Referral code** opens the code and partner-key page, after Reports to goodcryptoX and before Move or remove.
- **Move or remove goodcryptoX** has an arrow. It opens one page with three blocks one under the other, each with its title, its words and its button: **Move to another machine**, **Bring goodcryptoX from another machine** and **Remove goodcryptoX from this computer**, described next. The old addresses `/settings/move`, `/settings/bring` and `/settings/remove` still work: each opens this page at its block.
- **Quit goodcryptoX** is the last row where the computer offers it (a Linux desktop, which has no menu bar): it stops goodcryptoX properly, as the Mac's menu does, and asks nothing; goodcryptoX stays stopped until it is opened again from the applications menu; the page then says goodcryptoX has quit and how to open it again, not that it did not answer. It is never shown on a phone or another paired computer.
- **Move to another machine** (the first block) first asks you to install goodcryptoX on the other machine without connecting an account there. Export saves accounts, keys, bots, settings and history in one locked file. From that moment this copy places no new orders and sees no executions until the file runs on the other machine, where everything continues with the same API wallets. One Export opens the house passphrase dialog; the two guides give the same preparation-first order. The copy remains in this data folder if the browser download fails; after **Bring it back** or **Start fresh here** it is inside `moved-<date>/` with the rest of the old data. With no account set up here there is nothing to export: the block says so, shows no Export, and the two guides stand open with their steps.
- **Bring goodcryptoX from another machine** (the second block) is on the page whenever this runtime supports moving. Before accounts arrive it shows Loading; with none it has the file/passphrase form; with an account it links “export this one first” to Move. The Dashboard has a separate, dismissible optional Bring card first among optional cards, outside its progress ring, only while no real account is connected.
- **After an export**, opening any page shows one moved block with the date and file, **Bring it back** and **Start fresh here**. Bring opens the same form and keeps its fields on a refusal. Either accepted action shows “goodcryptoX is starting again” until the panel can load. Start fresh keeps the old bytes in `moved-<date>/` inside the data folder; the installation id, port and this browser’s sign-in stay. Bringing a file back also keeps this browser signed in.
- **Remove goodcryptoX from this computer** (the third block) first explains which local data is removed and what remains on the exchange. It is instructions only, as each system does it: on a Mac, quit from the menu bar, copy/delete the data folder, then move the app to the Trash; on Windows, uninstall goodcryptoX in Windows Settings › Apps, then copy/delete the data folder; on a Linux desktop, run `gcx uninstall` in a terminal, then copy/delete the data folder. With no account set up here it opens with “No accounts are set up here” instead of the consequence, and the steps are the same. Docker names `docker compose down` and both `gcx-data` and `gcx-secret` volumes. No removal button performs those actions. Orders and positions on Hyperliquid remain unaffected.

On Windows, if Startup apps has turned start at login off, its switch says **Turned off in Windows Settings › Startup apps**. Turn it on here to allow it again.

## Storage

Storage shows how much room goodcryptoX takes on this computer, where, and what you can delete.

The first row is the data folder's full path. On a Mac, **Show in Finder** opens that folder (and only that one); on Windows and a Linux desktop, **Show folder** opens it in the file manager. Docker and a server show the path without a desktop button.

**On this computer** is the folder's total, and under it its three parts, which add up to it:

- **History**: every account's orders, trades and bots.
- **Logs**: goodcryptoX's own record and its messages with the exchange, kept 14 days at most. The line under it, **At most 200 MB**, is the most Logs may take: press the pencil, type a whole number of MB (at least 50) and press the check or Enter; Esc or × keeps the old size. It applies at once, the oldest files going first.
- **Everything else**: update downloads, backups made before updates, a reserve for a full disk, keys and settings, and the room freed by deleted history until new history uses it. One row; its tooltip says what it holds.

The **History** card splits the History figure, shown again in its heading, **By account** or **By month** (the choice in the middle of the card; the browser remembers it). Its rows add up to that figure. Every size on the page is in one unit (MB once the folder passes a megabyte, never GB), with one decimal; a row too small for it reads **< 0.1 MB**. With no history yet the card says **Nothing stored**.

- **By account**: each account with its address and, once removed, a *removed* mark, then **Not tied to an account** (prices, runtime records and portfolio totals; no delete). **Delete** on a connected account says that a connected account keeps its history: remove the account to delete it. On a removed account it asks, then erases that account's orders, trades, bots and notes for good and restarts goodcryptoX; other accounts and any wallet they still use stay.
- **By month**: only the months that hold something, newest first, then the older years. **Delete** on a month or a year deletes it and everything older, never a month in the middle: pointing at it marks the rows it would erase, and it asks before it erases the orders, trades and bots that ended before the next month; open orders, running bots and all their cycles stay. It restarts goodcryptoX to do it. The current month has no Delete.

After you delete history the room it held stays in this folder: History falls by that much and Everything else grows by it, and the other rows keep their sizes. The figures of History are estimates from the size of each account's and each month's records. The first count shows **Counting…** with a bar. Counting runs only while the page and the browser tab are shown; General's Storage row reads only the folder's total.

## Preferences

Preferences contains **Language** and one **Trading** row. Trading opens **Trading defaults** then **Confirmation dialogs**. Runtime defaults refresh when reopened; browser confirmation choices stay cached. The old profile URL opens this same page, without an editor. Language is one row, "Language" with the language in use and a chevron (goodcryptoX's row); it opens the list, in English alphabetical order, with the native names, English names and a check on the current one.

Dates use your language’s order and month names, with the same month spelling in every browser. English short dates use **Sep**, and clocks stay in the existing 24-hour form.

## Opening protection

Installation has one switch after the keep-awake switch: on a Mac, **Ask for Touch ID to open the dashboard** where a platform authenticator is available or a passkey exists; on a NAS or a server, where the passkey belongs to the browser and not to the machine, **Ask for a passkey to open the dashboard**; otherwise **Ask for a passphrase to open the dashboard**. No separate credential fact line is shown. With no credential, enabling opens the normal dialog beside the switch: Create passkey, or two passphrase fields. Disabling performs the existing fresh check and keeps the stored credential. **Change passphrase** appears below the row only when a passphrase exists; changing one while protection is off keeps it off.

A Mac installation has no Passkeys page link. A plain Node install offers **Computers that can unlock** below the switch once a passkey or a passphrase is stored (with nothing stored there is no list to open, so the link is not drawn), with the existing key list and Remove actions. A Docker server keeps the switch, so **Not now** at the first opening can be undone there, but has no **Computers that can unlock** link: who may open it is set in Settings › Devices, `gcx passkey reset` removes its passkey and passphrase, and the list still opens at `/settings/passkeys`. The runtime still refuses removal of the last method while protection is on. Lock fallbacks and reset procedures stay the same.

- **Documentation** opens the documentation in a new tab.
- **Version history** opens the version notes: the current version first, then previous versions, each with its date. A heading is the version alone; the running build is named in Installation's version row. Future plans are not listed. Every version retains all three parts, such as **3.0.0**.
- **News by e-mail** opens the email field and **Send** for news about new versions. The Dashboard keeps its separate closable email card.
- **Terms of service** and **Privacy policy** open the built-in texts.

There is no separate About page: its old address opens General. The Dashboard’s update link opens Version history at the current release. A failed update check adds no message to Version history or Installation. The first-opening What’s new window keeps its version-only title and existing behavior. 

At the very bottom of General, small and centred like a website's footer: **Join us on Telegram · Follow on X · Contact support**; support opens an email to **support@goodcrypto.app**. The links wrap on a phone.

## Trading

**Trading defaults** comes first: what a new manual order starts with. Time in force is one year by default and at most one year. Its choices are 15 minutes, 1 hour, 8 hours, 1 day, 1 week, 30 days, 3 months, 6 months, 1 year and Custom. Custom replaces the menu with DD/MM/YYYY HH:MM; the × returns to the preset. A valid date shows how long remains; an error names the part to correct. The main order and its one TP/SL expiry field share this default. A date chosen for TP/SL remains that deadline; a duration preset begins when the entry fully fills.

**Reduce-only on TP / SL**, on by default, is here rather than in the forms. It applies to perps only, keeping an exit from flipping the position. Manual sends and exits added from Positions read the setting once; a new bot copies it when launched. Changing it does not edit resting orders, existing position exits or running bots. We recommend keeping it on. The main order's separate Reduce only option remains.

The Trade gear has these same two stored preferences, followed by Columns: Two / Three and Restore default layout. Changing a preference in either place reaches the other at once. A new form starts from the default, never the previous order's expiry; a currently chosen draft survives a preference change.

**Confirmation dialogs** follows: placing an order, cancelling an order, closing a position, changing an order (on the chart, and its take-profit and stop-loss from its details), closing a bot’s position by hand, placing failed averaging orders again, and placing an order again at its level. Every listed dialog has Don't ask again; ticking it turns this browser's corresponding Settings switch off. Each switch covers its action in every place: form, chart, list, details and Dashboard. Closing a bot’s position by hand has its own row. Turning the switch on restores the next question. The inline Send anyway warning confirmation remains separate.

The liquidation alert is on at 10% by default. Its switch and percentage also appear in the Trade cog; both edit the same setting. It reads as one sentence, "Alert when the price is 10 % from liquidation", with the percentage inside it, edited with the pencil like Notifications' "from level"; it must be above 0. While the switch is off the sentence still reads whole and the percentage cannot be edited. It alerts for active DCA and Grid bots holding perpetual positions. A saved percentage applies at the next price check. Turning it off keeps an approach remembered until the price leaves the selected distance; turning it on alone does not resend it. Manual positions and stopped bots are outside its scope. Reset restores on/10%.

Each section has its own quiet Reset to defaults button at the bottom left. The profile editor is absent in this release; its old URL opens Trading. The engine's stored profile and API remain compatible. A later release will offer an edit mode with eye icons for optional form fields; Time in force remains visible now.

## Alerts

Whatever you opened on a page (this token field, an account's **Edit account**, a list on the Dashboard, a row's details on Trade) closes when you leave the page: coming back shows the page as it first opens.

**Telegram** is read from your goodcryptoX when you open Alerts and again when you come back to the browser tab (while one-touch setup is waiting, it is also refreshed every three seconds while Alerts is visible; leaving the page or hiding the browser tab stops that timer). Until your chat is linked it is a card on top of the page; once it is linked the card is gone and the last row of the Telegram section (the third, after Orders and Bot defaults) takes over. What it shows depends on the bot:

- **No bot yet.** The card, titled **Connect Telegram to receive alerts**, says the two ways in two grey lines ("Press the button: goodcryptoX creates a bot for you. Confirm it in Telegram, and the bot writes to you" and "Or make your own bot in BotFather and paste its token here") with the green **Create my Telegram bot** at their right. Under them, **Enter your bot's token** opens a short field for the token BotFather gave you, with **Connect** at its right (off until the field holds a token); the card stays as it was above it. goodcryptoX asks Telegram whether the token is real before it keeps it, and the page says "Telegram refused this bot's token" under the token field if not. Without the one-touch settings in the build (every build has them), the field shows at once under the BotFather sentence. One press opens Telegram in a new tab with a bot ready to create, or the page says why it cannot. While goodcryptoX waits for you in Telegram the card adds one grey line under the button, **Waiting for Telegram** with a small spinner, which goes when the wait ends; a press while it waits opens the same link again and starts nothing. It turns to "Connected to @yourbot" after setup succeeds. Only a setup server that did not answer is told under Create my Telegram bot ("Our set-up server did not answer. Try again later"). Without both build settings, use BotFather.
- **A bot, no chat yet.** **Open your bot** opens the bot's chat in a new tab with a one-time code; press **Start** there, then come back. After one touch you are usually past this already: the **Start** you press in the new bot's chat within ten minutes links it. **Disconnect** is offered beside it, in case the token was of the wrong bot.
- **Linked.** No card: the Telegram section's last row says "Connected to @yourbot", with **Disconnect** as a red word at its right; it tells your chat, forgets the bot and stops the messages.
- **Trouble.** If you blocked the bot, Telegram refused its token, or another copy of goodcryptoX reads the same bot, the card says so and offers **Re-check** and **Disconnect**. Re-check cannot clear a revoked token: Disconnect, then connect the new one.

The Telegram section's two switches, above that row, are for the shortcut buttons that goodcryptoX's Telegram messages carry:

- **Shortcut buttons in messages** (on at first). Off, the messages carry no buttons.
- **Ask before a Telegram shortcut acts** (on at first; shown only while the first is on, indented below it). On, a button first says in the message what it is about to do and acts only after you press Confirm. This guards against a mistaken tap. It does not guard against another person: anyone who can use your Telegram can confirm too. If someone else can use your phone or your Telegram, turn the shortcut buttons off.

**Orders** has two switches, both on at first: **Manual orders placed from goodcryptoX** (the fill and the trigger of your manual orders) and **Orders placed outside goodcryptoX** (a fill of an order you placed with the exchange's own app or another tool, sent with "(external)" in its title). **For new bots** has the switches a new DCA bot starts with: **Bot stops or errors**, **Take profit and stop loss fills**, **Entry and averaging orders**, one row that reads "Entry and averaging orders from level 4" while its switch is on, the number with a pencil that edits it in place (0 is the entry order; a whole number of 0 to 100); with the switch off the row is just the label. The bot form shows them and you may change them for that bot alone; a bot that exists keeps its own.

Each is saved as soon as you press it, in your goodcryptoX, and stays as you left it. While goodcryptoX has not heard from the runtime the card waits with a centred spinner and, when the runtime goes quiet, the last card greyed with no button to press and the switches greyed. See [Telegram: your own bot, in one touch](../notifications/telegram.md).

## Exchanges

The list of exchanges, each with its logo in its colours and its state in a column of its own: **Ready** for one account that can trade (the card says "Ready for trading"), **Not approved** when its builder fee is not approved, the account's own word where something else is wrong (Key Error, Error, Waiting for approval), "N accounts" for several (with a warning sign if one has a problem), "not configured" when none is connected. Click it to see your accounts.

### Your Hyperliquid accounts

One card per account, two to a row. A sub-account or a vault comes right after its main account.

- The account's **name** and address, and its **exchange balance** in USDC (named by its coin, as on the Dashboard and Trade): the USDC total goodcryptoX reads from Hyperliquid, written as goodcryptoX wrote it here (no cents from 100 up: "3,465", "26.8k" from 21,000, "10.83" below 100; the Dashboard and the lists keep their cents), or "Could not be read yet; the runtime keeps trying." when it cannot be stated.
- **One status line**: a green check and **Ready for trading** when the account is configured, connected and can trade. When something is wrong the check becomes a warning mark with what is wrong and what mends it: "Builder fee not approved · **Allow builder fees**", "Your Hyperliquid API wallet has expired. Replace it to avoid trading interruptions · **Fix**", Key Error or Error, or, as a spinner and not a warning (goodcryptoX itself planned the wait), "Waiting for approval · **Try again**" while Hyperliquid does not list the account's new API wallet yet; Checking... while it is being checked.
- For a main account: its **API wallet** on one line, "API wallet: gcx · expires March 30, 2027" (the key goodcryptoX trades with; it can trade but never withdraw; see [Safety and keys](../concepts/safety.md#the-api-wallet); the day is written out in your language, with no clock). From 30 days before expiry a red notice says so, with **Fix** to replace the API wallet. Then the **builder fee**: "Builder fee 0.03% · approved" (0.03 % of each trade's value is what goodcryptoX charges). If you approved more than that earlier (a key approved up to 1 %), hold the pointer on the line: the tooltip says "Builder fee approved up to 1%; goodcryptoX charges 0.03%". "Max builder fee unknown" when goodcryptoX could not ask Hyperliquid just now: nothing is refused for that, and goodcryptoX asks again each time you open Settings. An approval you made earlier (in goodcryptoX, for the same builder) shows as approved as soon as the account is connected.
- A **sub-account** trades with its main account's API wallet and goodcryptoX's 0.03 % fee, as its main account (the card's second line ends "of" and the main account's address). If Hyperliquid refuses the fee on one of its orders, that order ends with Hyperliquid's words and you are told where to approve; the account's next order is sent as usual, with the fee ([Sub-accounts and vaults](../venues/hyperliquid.md#sub-accounts-and-vaults)).
- A **vault** you lead trades as a sub-account does; its balance counts your own share of it.
- A main account whose balance is 1 dollar or less while one of its sub-accounts has a bot of goodcryptoX running says in red: "Keep funds on the main account: sub-accounts' API wallet depends on it" (Hyperliquid removes the API wallet of every sub-account when the main account holds nothing).
- An account being removed says what it waits for: "Removing: waiting for Hyperliquid's answer to N order(s)" (orders goodcryptoX sent that Hyperliquid has not answered yet), or, when it removes the API wallet from Hyperliquid, that it waits for your wallet to remove it, with **Try again**.
- **One API wallet per main account**, shared by every account you add under it: each card shows that API wallet (its expiry, **Fix** when it expires soon, the builder fee). Renewing it or allowing the builder fee from any of these cards does it once for all of them, and your main account's wallet signs. The main account itself is an account like the others: it can be left out of goodcryptoX while its sub-accounts and vaults trade on.
- Under each name, the kind and the address shortened to its first six and last four characters with five asterisks between, as goodcryptoX did elsewhere, alike for the three kinds: a main account "Main account · 0x1234*****abcd"; a sub-account "Sub-account · 0x9876*****5432 · of 0x1234*****abcd" (its own address, then its main account's; its name is the card's title above), a vault "Vault · 0x9876*****5432 · of 0x1234*****abcd". Sub-accounts and vaults are not listed on this page until you add one: **Add Hyperliquid account** shows them in the account list ([Connecting your Hyperliquid account](connect.md#the-account-list)); the page reads nothing from Hyperliquid when you open it.
- Under the status, in the card's own type: **Include in balances** and **Include in PnL**, each with its switch (a vault has the first only; see [Include an account in Dashboard results](#include-an-account-in-dashboard-results)).
- **Edit account** (the closed row reads just that: goodcryptoX's row read "Allow builder fees, Edit account", but the status line above now carries that action) opens with one line naming the API wallet the account trades with, "API wallet gcx · 0x7c9d*****61e3" (the card does not carry it), then, each with an outline icon: **Rename account** (the form opens with the current name in the field, up to 50 characters, and returns to the accounts when you save; an empty field changes nothing); **Allow builder fees** (when not approved yet), **Replace API wallet** (replace the API wallet of its main account with a new one, for every account under it; your main account's wallet signs) and **Remove account**, in red (opens a dialog: goodcryptoX stops following the account; its box **Also remove the API wallet from Hyperliquid** decides what happens to the API wallet).
- **Add Hyperliquid account** after the last card, a tile of its own text and a chevron: connect your main account's wallet (it signs nothing when goodcryptoX already holds it) and pick what to add. You can connect up to 100 accounts. While the steps run, the card keeps its title with **Cancel** at its right, and each step is a row of its own. The terms and privacy line is not repeated here: you agreed once, under **Connect automatically** with your first account.

When the data behind an account stops updating, the page shows one notice "Not up to date" for the whole page, and the values stay greyed.

**Connect automatically**, **Add Hyperliquid account**, **Try again** and **Allow builder fees** run the connection's steps in place with your wallet: see [Connecting your Hyperliquid account](connect.md). **Replace API wallet** and **Fix** on an expiring API wallet renew it ([Safety and keys](../concepts/safety.md#the-api-wallet)).

### Removing an account

**Remove account** removes that one account, whichever it is, the main account included, and asks first in a short dialog: the title **Remove** and the account's name, what of it is open on the exchange, two boxes, **Remove** (in red) and **Cancel**:

- goodcryptoX removes the account from itself and leaves the exchange as it is: resting orders stay on the orderbook, positions stay open, nothing is cancelled or closed. One sentence says what is open, from what goodcryptoX knows: "2 bots and 3 orders are still open on Hyperliquid. goodcryptoX stops watching them; the bots stop, the orders stay as they are" (or the bots or the orders alone, or "Nothing of this account is open on Hyperliquid"). The orders counted are those resting on Hyperliquid; when goodcryptoX watches stops or trailing stops of the account itself, a second line says they end with it ("The 2 stops goodcryptoX watches itself end with it"): they are not on Hyperliquid.
- Its running bots stop with **Error** and the reason **Account removed** (nothing cancelled or closed); Telegram tells you once per bot under the stops switch ("DCA Error: …, The bot stopped: its account was removed from goodcryptoX …"). Its resting orders read **Left on Hyperliquid** in History.
- **Keep trading history**, unticked by default. Ticked, the account's bots and orders stay in Bots and History at their places, marked "Scalping (Account removed)" under All pairs and accounts, and offer no action; adding the same address back brings the same account, its rows unmarked, its bots as they ended. Unticked, everything of the account leaves the lists, History and the details at once, and is erased for good at the next start: the box's help line says "Unticked, every order, trade, bot and note of this account is erased from goodcryptoX for good; goodcryptoX restarts to do it. This cannot be undone". Once the remove ends, the notice reads "Deleting: goodcryptoX restarts to erase it. If you started goodcryptoX in a terminal, start it again" goodcryptoX stops (as for an update: the stops it watches itself on your other accounts are not watched for those seconds; Hyperliquid's own stops keep working) and, as it starts again, before anything trades, erases the account's rows: its orders, trades, bots, funding, notes, the copies of its Telegram messages and its stored reports, and the backups made before updates. One line stays in the database: an account's data was deleted, with the date and the number of rows. When goodcryptoX is updating or moving to another machine at that moment, or the erase fails (a page says so), it happens at the next start. Each account goes alone: a main account's own record (its address and name, hidden) stays while a sub-account or vault still uses its API wallet, and goes with the last of them. The address added back is a new account. goodcryptoX's own remove had no such line: it kept nothing on your computer. Either way the account leaves the Dashboard's totals and lists at once, and its positions leave the positions list and Close all.
- **Also remove the API wallet from Hyperliquid**, unticked by default; its line says what unticked leaves: "Unticked, goodcryptoX's API wallet stays approved on Hyperliquid until it expires or you remove it there". Ticked, when other accounts use the same API wallet, a line names them: "Hyperliquid-3 and Hyperliquid-5 use it and will stop trading" (and how many stops goodcryptoX watches itself on them can no longer be sent). After **Remove**, your main account's wallet asks you to sign once: it removes goodcryptoX's API wallet from Hyperliquid, and the account is removed once Hyperliquid no longer lists it. The other accounts then stop trading as with an expired API wallet (below): their new orders and bots are refused, their bots keep their orders on Hyperliquid, goodcryptoX keeps showing and booking them, and a bot stops with **Error** when Hyperliquid refuses its next order; renewing the API wallet from any of their cards trades them again. If you decline in the wallet or Hyperliquid refuses: **Try again**, or **Remove without revoking** (the API wallet stays approved on Hyperliquid until it expires or you remove it there). The account is being removed from the moment you press **Remove**: the last button then reads **Close**, and the card's **Try again** asks your wallet again.
- goodcryptoX deletes the API wallet's key from your computer with the last account under its main account (revoked first when that account's box, or another's still waiting, asks it).
- An order goodcryptoX sent that the exchange has not answered yet is waited for first (the card says so). A remove that a restart interrupts goes on by itself; the account never trades again meanwhile.

### When the API wallet expires or is no longer approved

goodcryptoX reads the API wallet from the exchange's own list when it starts, before each new bot and each bot cycle, when the exchange refuses an order for it, and when you renew it; after the expiry date the exchange gave it, goodcryptoX counts it as expired. When it has expired, or the exchange no longer lists it (a main account that holds no funds loses its API wallets), nothing is held, as in goodcryptoX: a new order or bot on that main account or its sub-accounts and vaults is refused with "Your API wallet for … has expired: renew it in Settings." (or "… is no longer approved on {venue}: …"), shown on the Trade page in place of Buy, Sell and Launch; a running bot's order goes to the exchange, which refuses it, and the bot stops with **Error** and the exchange's text (as goodcryptoX); a stop that fires is refused the same way and waits in repair. Your other main accounts are not affected. A wallet the exchange no longer lists is told once in a page. Once you renew it (**Replace API wallet**, or **Fix**; fund the main account first if the exchange removed it for holding nothing), new orders and bots are taken again as soon as the exchange lists the new one.

## Proxy

Open **General › Installation › Proxy**. Its Installation row shows **Off**, or the host when on. Turn **Proxy On**, enter a SOCKS5 or HTTP address and **Save**. With no address saved, only Save turns it on. With an address saved, the switch saves at once; **Off** keeps the address for next time. The saved address masks its password and keeps the host readable. **Edit** opens it with **Save** and **Cancel**; saving the masked address keeps its login. **Remove** clears the address and turns Proxy off. Empty fields show no warning; an address that is not a SOCKS5 or HTTP address warns at the field after Save and is not saved. The same setting works on a computer, a NAS and a server. Open account streams reconnect without a restart. A failure alerts you and never blocks an order form. See the [proxy guide](../install/_proxy.md) for addresses with a login, `GCX_PROXY` and the Gluetun recipe.
