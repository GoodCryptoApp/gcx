# Local API

It runs inside `gcx run`, which the Mac app and the Docker image start.

goodcryptoX runs one program on your computer (or NAS or server). The panel you open in the browser, and any AI agent or script you use, talk to that program through its local API. This page describes what it accepts and what it refuses.

## Where it listens

Only on this computer (`127.0.0.1`, which the name `localhost` also reaches), on the port chosen at install. Nothing on your network, and nothing on the internet, can reach it directly. If another program already uses the port, goodcryptoX keeps running your bots, tells you (in the log, and in `gcx open`), and tries the port again every 30 seconds.

Reaching the panel from your phone through Tailscale needs a passkey, which this version does not offer yet: until then every request that came through a proxy is refused.

## Signing in on this computer

On a Mac, click **Open the dashboard** in the goodcryptoX menu in the menu bar, or run:

```
gcx open
```

It opens your browser on a link such as `http://localhost:8118/login#…`, which signs in and opens the panel at `http://localhost:8118/gcx` (browsers send `localhost` to your own computer). A page at `127.0.0.1` or at the earlier `gcx.localhost`, and any page address outside `/gcx`, leads there; the API and the panel's files answer where they are asked. `gcx open --print` only prints the link, for a session over SSH (on a Linux desktop `gcx open` opens the browser with `xdg-open`, starting goodcryptoX first when it is stopped; with no graphical session, and on Windows for now, it prints the link); in Docker it adds the SSH tunnel line with this goodcryptoX's port. The part after `#` is a one-time code: it works once, for 60 seconds, and never reaches any server log because browsers do not send that part. The page swaps it for a sign-in cookie and removes it from the address bar.

Only a program running under your own user account can ask goodcryptoX for a code: `gcx open` talks to goodcryptoX through a socket in the data folder that only your account can open. That is tested on macOS and holds by the same file permissions on Linux. On Windows it is a named pipe with Windows' default permissions (Node cannot set others), named from the install id in `install.json`, which only your account can read, so another user cannot take the name first; it has not been tested there yet.

The data folder is `~/Library/Application Support/GCX` on a Mac and `${XDG_DATA_HOME:-~/.local/share}/gcx` on Linux; `--data <folder>` or the environment variable `GCX_DATA` names another (on Windows one of them is needed for now).

The other commands on the same channel:

| Command | What it does |
|---|---|
| `gcx run` | Runs goodcryptoX itself in the foreground, on the data folder that `gcx install` prepared, until `gcx stop`, Ctrl-C or the system's stop signal; then it finishes what is under way (at most 30 seconds) and exits with code 0. Any other end, a crash included, exits with another code. gcx.app runs it for you. |
| `gcx install` | Makes the data folder, picks the panel's port (8118, or the next free one when another program holds it) and an install id, and keeps both in `install.json` there, and turns on "Start goodcryptoX when I log in" the first time, and again when the installed version changes (a new copy of the app over an old one loses it), unless you turned it off in Settings or in System Settings; `install.json` keeps the version that last ran install (`installedVersion`) and your "off" (`loginItem`). Running it again by the same version changes nothing (a folder from before the install id gets one, its port kept). gcx.app runs it every time it starts. Run from the unpacked Linux download, it also copies the program to `~/.local/opt/gcx`, writes the `gcx` command in `~/.local/bin`, the systemd user unit `gcx.service` and the goodcryptoX entry of the applications menu, enables and starts the unit, and opens the browser ([Set up goodcryptoX on Linux](../../install/linux.md)). With `--docker`, the image runs it at every start instead (0024): the port is 8128 or the next free one, no login item is touched, the secret that unlocks the key store is made once in `$CREDENTIALS_DIRECTORY` (the image's `/secret`) and kept after, a secret there that cannot be read stops the start with the reason, and it prints only the data folder: `gcx run` then writes the way in to the container's log (below, `gcx pair`). |
| `gcx status` | Says whether goodcryptoX is running, with its process number, the panel's address and its version (`gcx is running (pid 123): http://localhost:8118/gcx, version 3.0, Build 2312`; a build made on a branch or with changes says `Build 2312 dev`); exit code 1 when it is not. |

| `gcx rollback [<build>]` | Goes back to the previous published build, or to the older one named by its build number, with goodcryptoX running: goodcryptoX downloads and checks it as an update, prints how many internal stops and trails will be unwatched for a few seconds (and, for a build older than the previous one, that it may not understand what this version wrote), then drains and restarts as that build (on a Mac the app's helper swaps it in). Only the program goes back; the data folder is kept as it is, and the build left is not reinstalled until **Try again** in Settings › General › Installation. It refuses a development build, a build not older than the running one, and one not published or withdrawn, with the reason. In Docker it asks no running goodcryptoX and prints the `compose.yaml` image line with the build's tag and `docker compose up -d`. See [Updates](../../updates.md#going-back-to-the-previous-build). |

Updates by themselves then follow that tier, newer builds only. Only tiers up to the highest this installation has run; on a Mac only today. See [Updates](../../updates.md#internal-beta-and-everyone). |
| `gcx passkey reset` | On a NAS or a server: removes the panel's passkey and passphrase on this computer, signs every browser out, and prints a fresh sign-in link that opens the first-time screen ("Protect goodcryptoX on this computer"). The setting Ask for the passkey on this computer stays as it was; phones are not touched. The lock screen shows the exact line, with Copy: in Docker `docker exec gcx gcx passkey reset`, typed on the machine; elsewhere the runtime's own Node and script, and `--data` when the data folder is not the system's, over SSH. With goodcryptoX not running it says "goodcryptoX is not running. Start it, then run this again." On a Mac it refuses and says "Open the goodcryptoX menu in the menu bar and choose Reset passkey… (it asks for your Mac's password).": the menu item asks for the Mac's password or Touch ID first, then does the same. |
| `gcx pair` | Asks the running goodcryptoX for a fresh pairing link for a phone or another computer and prints it with its QR code: it works once, for 10 minutes, the one before it void, and the device it pairs starts at Can trade. On a server it is the way back in when every device is lost (the container's terminal, or `docker exec gcx gcx pair`). Under Docker, `gcx run` writes the same block first in the container's log while no device is paired ("Add a device: …" once one is), then one "Engineers:" line with the SSH tunnel and `gcx open --print`; these lines go to the container's output, never to the log files. |
| `gcx export [<file>]` | Moves goodcryptoX to another machine: says what stops (bots, internal stops and trails, orders resting on the exchange), asks a passphrase twice in the terminal, never on the command line, then the running goodcryptoX finishes what is under way, writes one encrypted file (in the data folder as `gcx-export-<date>.gcx` unless named, mode 600), reads it back, marks the folder moved; the command exits 0. With no goodcryptoX running on the folder the command does it itself. From then on goodcryptoX in that folder serves only the moved page (**Bring it back** or **Start fresh here**), and `gcx status` says "This data folder was moved to another machine on <date> (gcx export; the file: <path>). …". A failed export changes nothing. |
| `gcx import <file>` | With goodcryptoX stopped, on an install with no account, access key or partner code: asks the file's passphrase in the terminal and imports it (this machine's unlock secret made first, the key store written in the folder, the rest in place at once); the next start runs the imported ledger with the same API wallets. Refused while goodcryptoX runs (use the panel then), on a folder that has or had an account, or for a file of a newer goodcryptoX. |
| `gcx fold --data <folder> --out <file>` | Read-only, on a copy of a data folder (the release rehearsal runs it): folds the copy's journal with no exchange, no network and no key store and writes what it folds to, field by field, into `<file>`, with the rows it could not read by kind, how long it took and its peak memory. Opening the copy migrates it, as a start would; no row is added. Prints only counts and paths. Refused for this computer's own data folder, a folder goodcryptoX is running on, and a folder with no store. |
| `gcx uninstall` | Quit goodcryptoX from the menu bar first (on a Mac, a goodcryptoX the menu-bar item watches is started again after `gcx stop`). Then it stops goodcryptoX and turns "Start goodcryptoX when I log in" off. The data folder is kept and named: delete it yourself to delete your data. On a Linux desktop it also removes the unit, the applications-menu entry, the `gcx` command and the program. |

If the data folder's path is very long (over about 85 characters), the socket cannot be created; goodcryptoX says so, and `gcx open` cannot work until the folder has a shorter path.

Without a sign-in goodcryptoX serves only the sign-in pages and the tab's icon (`/favicon-dark.svg`, `/favicon-light.svg`, the `/favicon-theme.js` that picks between them, `/favicon-32.png`, `/favicon.svg` and Safari's `/apple-touch-icon.png`, which the browser asks for before anyone is signed in); everything else answers 401.

The sign-in lasts until you have not used the panel for 30 days. After that, or in another browser, run `gcx open` again. Links to the panel that you follow from elsewhere (a Telegram message, a bookmark) open signed in. A link opened in a browser that is already signed in keeps that sign-in (and whether it has confirmed with the passkey); it mints no second one. Another browser on the same computer can sign in with the passkey instead: where a passkey is stored and the protection switch is on, a browser with no sign-in at `http://localhost:<port>/gcx` sees the lock with **Unlock**, and the sign-in it gives has already confirmed.

## The passkey on this computer

A sign-in to the panel must also confirm it is you on this computer, unless the protection switch in Settings › General (**Ask for Touch ID**, **a passkey** or **a passphrase to open the dashboard**) is off. It confirms with a passkey (Touch ID, or the Mac's password in the browser's own sheet) made at `http://localhost:<port>`, or with a passphrase where a passkey cannot run (a browser without one). A passkey made at the earlier address `gcx.localhost` does not work at `localhost`: while it is the only one stored, the lock makes one anew and it replaces the old one: after the passphrase where one is set, otherwise with no check first, as at a first run (goodcryptoX cannot see the Touch ID that made a passkey). Not now and a new passphrase still need a check. It stays confirmed while a page of it is on screen (its socket holds the `runtime` topic) and for 5 minutes after the last one left the screen; then the next opening asks again. Until it confirms, every route but `GET /api/v1/passkey`, `POST /api/v1/passkey/challenge`, `register`, `verify`, `switch` and the two passphrase routes answers **401** `{error: "confirm it is you on this computer", verify: true}`, before anything runs or any body is read; so do the socket (its open sockets close within two seconds) and `POST /api/v1/runtime/unlock`. Access keys are not asked: they keep their own scope. The first passkey or passphrase can be set by any signed-in browser while none is stored (the first run, and after `gcx passkey reset`), and so can the switch (the first-time screen's Not now turns it off, and turning it on again asks for the screen at the next opening); after that only a confirmed one can add, with a check in the last minute. A wrong passphrase is answered no sooner than a second after it was taken up, one at a time for the whole of goodcryptoX.

## Connecting clients

Any AI agent or program can use this API with an access key from **Settings › API & Agents**. An MCP client uses the connector below; another program calls HTTP directly. Both reach the same API and use the same permissions.

### MCP configuration, transports and paths

The connector speaks MCP over standard input and output, not an HTTP MCP endpoint. Set `GCX_URL` to goodcryptoX's origin **without `/gcx` or `/api/v1`**, for example `http://127.0.0.1:8128`, and `GCX_KEY` to the access key. Use the address and port shown in **Connect**, rather than assuming the example port.

For a client that takes JSON configuration:

```json
{
  "mcpServers": {
    "gcx": {
      "command": "node",
      "args": ["<folder>/server/index.mjs"],
      "env": { "GCX_URL": "http://127.0.0.1:8128", "GCX_KEY": "<your key>" }
    }
  }
}
```

**Claude Desktop** downloads `gcx.mcpb`. It holds the loopback address of goodcryptoX, not your key; Desktop asks for the key during installation. The `.mcpb` is a ZIP: extract `server/index.mjs` to use the connector with another MCP client. Run it with Node 18 or newer: `node <folder>/server/index.mjs`. In a goodcryptoX container, `gcx mcp` starts the connector.

**Claude Code**, **Codex** and **Cursor** copy a command or configuration using the installed Node and connector paths. These buttons appear only when local connector paths are available. Replace `<your key>` in the copy. Codex's file is `~/.codex/config.toml`; Cursor uses `mcp.json`. **Other apps** shows the generic configuration.

The Claude Code command has this shape (both executable paths are supplied by goodcryptoX):

```sh
claude mcp add gcx -e GCX_URL=http://127.0.0.1:<port> -e GCX_KEY=<your-key> -- "<goodcryptoX's Node>" "<connector file>"
```

Use `claude mcp add --help` if your client's option syntax differs. The connector itself reads the key only from its environment, never a command-line argument to the connector.

When goodcryptoX runs on a server, NAS or in Docker, the executable and connector paths must belong to the computer running the MCP client. Download and extract the connector there and open the private tunnel described in [Set up on a server](../../install/server.md#sign-in) or [Set up on a NAS](../../install/nas.md#sign-in). Set `GCX_URL` to the tunnel's local end. The generated Desktop bundle uses `http://127.0.0.1:<port>` and works through that tunnel. Keep the tunnel open while making calls; bots and orders continue on the server when it closes.

If Desktop cannot connect, open **Claude menu › Settings › Developer** or inspect `mcp*.log`: `~/Library/Logs/Claude` on macOS, `%APPDATA%\Claude\logs` on Windows. The connector reports a runtime that is not running, an incorrect address, or an incorrect or revoked key.

### Direct HTTP and data

**Your own programs** shows the API address, including `/api/v1`, with **Copy**, **Show example** and **API reference**. Send the key as `Authorization: Bearer <key>`. The reference button opens `/api/v1/openapi.json`, filtered to operations that credential may call. HTTP does not require an MCP client.

All money, prices, sizes and percentages cross the API as decimal strings, not rounded JSON numbers. Encode decimal points with a dot: a sheet's `0,96 %` becomes `"0.96"`. When a snapshot topic has sent no data, the API reports **503 "not yet known"**. Treat it as unknown, not an empty list or zero, and retry later.

The connector offers these tools according to the key's scope. The [endpoint table](#endpoints) and served OpenAPI document describe their bodies and responses.

| Tool | What it answers |

| `instruments` | A venue's instruments with their trading rules; `q` keeps only those that match a coin or an id (`MU` finds `xyz:MU`) |
| `snapshot` | The current state of `orders`, `positions`, `bots`, `balances` or `account-state` |
| `order` | One order with its children, chain and events |
| `bot` | One bot with its plan, its orders of one iteration and its notification settings |
| `history` | Finished orders, newest first, a page at a time |

## Access keys

### Access keys: AI agents and scripts

Keys are made and managed only by a person signed in to **Settings › API & Agents**. The secret is shown once; goodcryptoX retains its SHA-256 fingerprint. Send it in `Authorization: Bearer <key>`, never in a URL. A request carrying both a sign-in cookie and a key is refused. A new scope or revocation applies from the next request; a revoked key's socket closes within two seconds.

| Scope | Permission |
|---|---|
| `read` | All readable accounts, instruments, orders, positions, bots, history, candles, cases, settings, topics, previews and the credential-filtered API description. Trading restrictions do not narrow reading. |
| `propose` | Read permission plus order and DCA/Grid bot proposals. Only the person can launch or reject them in the panel. |
| `trade` | Propose permission plus order placement, cancellation, modification of its own orders, leverage/margin-mode changes, and creation, modification, stopping and closing of its own DCA/Grid bots, within limits. |

No key can withdraw or move funds, change isolated margin or settings, manage keys, launch a proposal, read a bot's signal URL or command another owner's bot. A bot launched by the person from a proposal is not a directly key-owned bot.

### Limits and wire rules

`limits` contains `accounts: string[]`, `markets: string[] | "all"`, and decimal strings `perOrder`, `per24h`, `leverage`. Starting values are `"1000"`, `"10000"` and `"5"`; accounts and custom markets must be selected. Missing limits, empty selections or unset/non-positive numbers prevent trading. `markets: "all"` covers every market regardless of quote. The limits compare each market's quote value directly: 1 USDH, USDE or USDT0 counts as 1 USDC; this is not a currency conversion.

- **Order value:** goodcryptoX uses its own receipt and price. A market buy counts size at its possible fill bound: the book-derived bound, or 10% above the price when no level was read. A quote-sized spot buy counts its quote amount. Other orders, including market sells, use receipt value.
- **Exits:** a spot sell, perpetual Close or reduce-only order excludes the key's own holdings less its other resting exits (bracket legs counted once). Only the excess counts toward `perOrder` and `per24h`. Bot holdings are separate from these standalone-order holdings. An order that only reduces is not subject to the leverage limit.
- **Opposite-side orders:** a non-reduce-only order against an account's combined position is judged as on a flat market. A long of 1 ETH becomes 0.9 ETH after a sell of 0.1 ETH; permission is not confined to the key's own position.
- **Rolling usage:** fills counted by the limits in the last 24 hours plus the remaining open counted value. Cancellation returns the unfilled allowance. A modification is checked as a new order at its changed value and counted at that new value.
- **Leverage:** new risk-adding orders use the account's leverage at send; `expected` is accepted but ignored (deprecated). Leverage and margin-mode writes must fit the key's account, market and leverage permissions. The already-current setting returns `{"accepted": true}` without a venue write.
- **Brackets:** omitted `bracket.reduceOnly` means reduce-only, independently of Settings › Trading. An edit that omits it preserves the existing choice. Explicit non-reduce-only exits are allowed.
- **Exact close:** an order whose side and size exactly close the known account position is sent reduce-only even if the command omits that flag, and the limits judge it accordingly. A `close` command is sized from the account position.
- **Warnings:** trading-key orders pass form warnings without `overrides`; validation errors and key limits still refuse them. A limit order can be sent without a known market price. Preview returns warnings and errors but does not check key limits; placement does.

A key can cancel its own, the person's, another key's and external non-bot orders on allowed accounts. Cancel reach is account-based, not limited to its selected markets; limits must still be configured. It may modify only its own orders; another owner's or external order returns `key.order` for modification. A key's individual cancel of a bot order is refused even when the bot has stopped. The person can cancel a stopped/errored bot's leftover order, and a DCA exit during repair. These person exceptions grant no permission to a key.

### Bots and proposals

`POST /api/v1/bots` takes `botCreate` from the served OpenAPI document; use `kind: "grid"` for Grid. `POST /api/v1/bots/preview` / `preview_bot` shows the planned orders at current prices without creating a bot. Each DCA entry/averaging order or Grid opening order must fit `perOrder`. The DCA ladder or all Grid opening levels count up front against remaining `per24h` for each cycle. New cycles use current account, market, order and 24-hour limits. Leverage is checked at launch and key Modify, not reimposed at each running cycle.

Omitted bot `leverage` and `marginMode` use the open position's values, otherwise isolated 5x. A failed required position read returns 503, "The position could not be read. Try again.", with no bot or venue write. A bot can trade against the account position within its limits; Telegram reports the opposite size at cycle start. Its reduce-only exits may be refused while the account position remains on the other side, requiring repair. On spot, a supported bot sell can use coins held on the account within the same limits.

`wholePosition` ("Only this bot trades {instrument} in this account") is an advisory mismatch check, not an exclusion of other trading or a sizing control.

A cycle over its allowance waits at `key-limit` and resumes automatically when allowance frees, with Telegram notices on the wait and resumption. Its existing exits remain. A key's `bot_command` permits its own `stop` (optionally `close: true`), `force-close` and `modify`; DCA also permits `end-iteration` and `modify-clear`. End-iteration closes now and a repeating DCA bot can start again; force-close closes what a stopped bot holds. Modify checks the complete candidate as a new launch; current-cycle usage is retained. Other commands and other owners' bots are refused.

Suspend persists the stopped permission, cancels resting risk-adding orders and pauses key-owned bots, leaving positions and protective exits. Resume continues the bots and allows new commands; it does not recreate cancelled standalone orders. Revoke applies the same pause/cancellation permanently and ends reading as well. Bots remain paused until the person stops them.

At most **20 proposals wait per key**, shared across order, DCA and Grid kinds; another proposal returns 409 until the person launches or rejects one. There is no expiry. Lowering scope to `read` or revoking rejects waiting proposals, including one already open in a form. Proposal fields omitted from the command take the form's documented defaults, not its remembered draft. Only the proposal side's form action launches it; the other side places a person order and leaves it waiting. A refused launch remains waiting. Key details retain proposals and outcomes, activity, and PnL from direct orders and launched proposals.

### Request rate

Each key may send **20 requests per second**. The 21st returns 429 with `Retry-After: 1`; keys count separately and signed-in people have no such limit. There is no separate per-second write limit or daily change count imposed by goodcryptoX; venue limits pace writes alongside the person's orders.

"Last used" may lag after a crash: it is flushed at most once a minute and at shutdown.

## What is refused

| Request | Answer |
|---|---|
| No sign-in cookie and no access key, or a key that is unknown or revoked | 401 |
| A sign-in that has not confirmed with the passkey on this computer, on anything but the passkey's own routes | 401 `{error, verify: true}` |
| An access key on a route its scope does not allow (including key management and a bot's signal URL) | 403, before the body is read |
| More than 20 requests in one second from one access key | 429, with `Retry-After: 1` |
| A trading key's command beyond its limits | 422 `{rejected: "key.…", text}` with the limit and the numbers |
| A trading key's command after you suspended or revoked it, even one already on its way | 403 `{rejected: "key.suspended"}` or `key.revoked` |
| A `Host` other than `localhost`, `127.0.0.1`, `[::1]` or the earlier `gcx.localhost`, each spelled exactly and with goodcryptoX's port (a site that points its own name at your computer; `evil.localhost` is refused too) | 403 |
| Any `X-Forwarded-…` or `Tailscale-…` header, including Tailscale Funnel (the panel published to the internet) | 403 |
| A page from another origin (another site, or another program on your computer) that sends a write or opens the socket | 403 |
| A write or a socket from the browser with neither `Origin` nor `Sec-Fetch-Site: same-origin` | 403 |
| A read carrying another origin's `Origin` | 403 |
| A body over 256 KiB (4 MiB on the two chart layout writes) | 413 |
| A body that does not match its schema | 400, with the reason |
| A chart layout write while the disk reserve is spent or the disk is full | 507, nothing written |

Reads (GET) never change anything, and goodcryptoX never sends the headers that would let another site read an answer (CORS). Every answer says `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY` and a `Content-Security-Policy` under which the panel runs only goodcryptoX's own scripts (plus the three the chart library writes into its own frame, pinned by their hashes), no other site may frame it, and the only other hosts it may reach are the wallet connection's (Reown's and WalletConnect's); API answers also say `Cache-Control: no-store`. A page at `127.0.0.1`, `[::1]` or the earlier `gcx.localhost` is redirected to `http://localhost:<port>/gcx`, the address you are given, which keeps its own sign-in and form memory.

Honest limit: cookies do not distinguish ports, so another web server on `localhost` or `127.0.0.1` that your browser visits receives the goodcryptoX sign-in cookie, and that program can then act as you on the panel, orders included. The Origin rule refuses what its pages send from your browser, not what the program itself sends with the cookie. It is a program on your own computer: only run web servers there that you trust.

### Trading responses

| Status | Meaning |
|---|---|
| 200 | `{"id": ...}` placed, or `{"accepted": true}` |
| 422 | `{"rejected": key, "text": ...}`: refused. A validation or key-limit refusal before durable acceptance sends nothing, and the same `requestId` may be retried after a change. A committed request retains its identity and answer. When the exchange itself refused a margin change or the cancel of an order placed outside goodcryptoX, `text` is our sentence (in the `language` setting) and `raw` is the exchange's own words unchanged. |
| 403 | the scope does not allow this, or a command was stopped by suspension/revocation after authentication |
| 409 | this `requestId` was used before with another body, or the key already has 20 waiting proposals |
| 429 | more than 20 requests in a second; try again in a second |
| 503 | goodcryptoX cannot take the command now, a required read is unavailable, or a required price is unknown. A limit order may be sent without a market price; retry according to `text`. |
| 401 | the key is unknown or revoked |

A trading key's own refusals, with their texts:

| `rejected` | Text |
|---|---|
| `key.noLimits` | This key has no limits yet. Set them in Settings › API & Agents. |
| `key.account` | This key may not trade on hl-main. |
| `key.market` | This key may not trade BTC. You can propose it instead. |
| `key.perOrder` | Order value 1,240.00 USDC is over this key's limit of 1,000.00 USDC. You can propose it instead. |
| `key.per24h` | This key has used 9,800.00 of its 10,000.00 USDC for the last 24 hours; this order needs 400.00. You can propose it instead. |

A bot creation with an unavailable optional preflight check returns its sentence as `warning` for a key. The person's request returns 422 `unread` and can be confirmed with `anyway: true`. This differs from a failed required position read, which returns 503 and creates no bot.

Any other `rejected` is the same check the panel's order form makes for you, with its text in goodcryptoX's words.

### Four warnings a program meets

A key's order is sent with any of them; the preview names them, and the exchange's answer is the answer.

| Warning | When | What happens |
|---|---|---|
| "You are trying to buy at the price higher than the market" (or sell lower) | a limit through the market to cap slippage; a buy at the best bid while the last trade is below it | sent: it rests, or fills up to its price |
| "Buy price will be higher than the market!" (or sell lower) | every ordinary stop-limit (sell stop 3,000, limit 2,990) | sent: goodcryptoX fires it at the trigger as for you |
| "TP size is lower than minimum amount allowed by the exchange" | a take-profit split into parts under the market's minimum (for example 10 USDC) | sent: the exchange may refuse the small parts when they are placed |
| "Order value cannot be less than {minimum} {quote}" | an order under the market's minimum | sent: the exchange judges it. An exact full-position close sent reduce-only may qualify for the venue's minimum-size exception. |

| `POST /api/v1/devices/pair` | you | `{}` | a pairing link that works once, for 10 minutes, the one before it void: `{link, expiresAt}`; a device paired with it starts at Can trade |
| `POST /api/v1/devices/pair/cancel` | you | `{}` | `{}`: the dialog closed, its link stops working (a link from `gcx pair` stays) |
| `POST /api/v1/devices/{id}/rename` | you | `{name}` (1 to 50 characters) | the row as it is now; 404 for a device not paired |
| `POST /api/v1/devices/{id}/switch` | you | `{canTrade}` | the row as it is now; the device obeys it from its next request; 404 for a device not paired |
| `POST /api/v1/devices/{id}/remove` | you | `{}` | `{}`: the row gone, the device's open sessions closed within a second; 404 for a device not paired |

Every command (an order, a cancel, a modify, a bot command, a leverage or margin change) reaches goodcryptoX with who sent it, worked out from your sign-in, never from the body.

Every write carries a `requestId` you choose; goodcryptoX makes one order (or one change) per id, so sending the same command again after a lost answer is safe, also after goodcryptoX restarted: the id is written with the order, in the same step. The same id with a different body is refused (409), never answered with the first body's answer. A refused command is not remembered: sent again, it is checked again. A leverage, margin or external-cancel request is written before it is sent, so one the exchange refused, or one it rate-limited four times (never executed), is answered with that refusal when sent again (422), and one whose reply was lost is answered `accepted` when sent again and is never sent again: what Hyperliquid did shows in the topics. An order is checked against goodcryptoX's own prices, balances, position and leverage after that de-duplication, never before it; a Close is sized by a fresh read of your position.

## Worked order example

Send the order command (its schema is in the OpenAPI document goodcryptoX serves at `/api/v1/openapi.json`) to `POST /api/v1/orders` with the key in the header, every number as a string, and a `requestId` of your own: new for each new order, the same when you retry after no answer, so a retry never places twice. First ask goodcryptoX which accounts you have (`GET /api/v1/accounts`) and put one's id in `sourceId`.

This example buys 90 USDC of ETH at a 3,000 limit, with a 3% take-profit and 1.5% stop-loss; both exits are reduce-only. Assume the last price is above 3,000, the account and ETH are allowed, there is room within the rolling allowance, and the market is set to 3x cross. The amount is within the starting order limit:

```json
{
  "requestId": "my-strategy-0001",
  "sourceId": "YOUR-ACCOUNT-ID",
  "instrumentId": "ETH",
  "type": "limit",
  "side": "buy",
  "size": "90",
  "sizeUnit": "quote",
  "price": "3000",
  "overrides": [],
  "bracket": {
    "reduceOnly": true,
    "tp": { "type": "market", "mode": "percent", "targets": [{ "value": "3", "share": "100" }] },
    "sl": { "type": "market", "mode": "percent", "value": "1.5" }
  }
}
```

With `curl`, the key in `$GCX_KEY` and the body above in `order.json`:

```sh
curl -s -X POST http://127.0.0.1:<port>/api/v1/orders \
  -H "Authorization: Bearer $GCX_KEY" -H "Content-Type: application/json" -d @order.json
```

In Python:

```python
import json, os, urllib.error, urllib.request
order = json.load(open("order.json"))
req = urllib.request.Request("http://127.0.0.1:<port>/api/v1/orders", data=json.dumps(order).encode(), method="POST",
                             headers={"Authorization": "Bearer " + os.environ["GCX_KEY"], "Content-Type": "application/json"})
try:
    print(json.load(urllib.request.urlopen(req)))        # {"id": "o12"}
except urllib.error.HTTPError as e:
    print(e.code, json.load(e))                          # 422 {"rejected": "key.perOrder", "text": "..."}
```

In JavaScript:

```js
const order = JSON.parse(await (await import("node:fs/promises")).readFile("order.json", "utf8"));
const r = await fetch("http://127.0.0.1:<port>/api/v1/orders", { method: "POST", body: JSON.stringify(order),
  headers: { authorization: `Bearer ${process.env.GCX_KEY}`, "content-type": "application/json" } });
console.log(r.status, await r.json()); // 200 {id} or 422 {rejected, text}
```

To set leverage first, send `POST /api/v1/leverage` with `{"requestId": "...", "sourceId": "...", "instrumentId": "ETH", "leverage": "3", "marginMode": "cross"}`. The order uses leverage at send, not a caller's `expected` value. To cancel, send `POST /api/v1/orders/<id>/cancel` with `{"requestId": "..."}`; percent-encode the id as one segment (`x1/tp1` becomes `x1%2Ftp1`). MCP tools encode it for you. [Access keys](#access-keys) describes order modification, bracket defaults and exact closes.

### Cancel all and Stop all

`POST /api/v1/orders/cancel-all` cancels every open order on the accounts ticked for the key that matches a filter (yours too; with no limits set, `key.noLimits`), `POST /api/v1/bots/stop-all` stops every running bot it created that matches one; each is one cancel or one Stop per order or bot, as if sent alone. A bot's order is never cancelled by Cancel all: it is listed in `refused` with why (`text`, and `code: "bot-order"`, which the panel says in its language), and the bot's Stop cancels it; a key's individual cancel returns 422 `{"rejected": "bot-order", "text": …}` even after the bot stops. Only the person may individually cancel a stopped or errored bot's leftover order; the key uses its allowed bot commands. The person may also cancel a DCA take-profit or stop-loss during repair; the bot treats that as an exchange cancellation and asks to repair that exit. Every filter field is optional: `sourceId`, `instrumentId`, `side` (`buy`, `sell`), `type` (orders: `market`, `limit`, `stop-market`, `trailing`, `liquidation`; bots: `dca`), `status` (an order's `planned`, `sending`, `open`, `unknown`; a bot's state), and for orders `source` (`ours`, `external`), `q` (the lists' search text) and `children`. With none, "all" is every open order on the key's accounts, and every bot of this key: a key never stops another key's bot or your own. The answer names what was done: `{"count": 2, "ids": ["o1", "o4"], "refused": []}`; `count: 0` means the filter matched nothing and nothing was cancelled or stopped. The panel's Open orders and Bots lists have the same two shortcuts for you, acting on what the list's filter shows.

### Close all

`POST /api/v1/positions/close-all` closes every position on the accounts ticked for the key that matches a filter (`sourceId`, `instrumentId`, `side`, `q`), yours too: each is one Close as if sent alone (the whole position at market, read again when it is sent), so it is judged by the key's limits like any Close, and a key with no limits gets `key.noLimits`. A bot's part of a position (a running bot's, or a stopped bot's that still holds it) is never sold. With `bots: "keep"` (the default) it is listed in `refused` with `code: "bot-position"` and the rest of that position is closed: the exchange's size when it is sent less what the bots hold (`code: "below-minimum"` when that is under the exchange's minimum order value). With `bots: "stop"` the rest is closed the same way, then each bot the key created is stopped with its position closed, and the answer adds `"bots": [{"botId": "dca1"}]`; another's bot is left (`bot-position`). The `positions` topic's rows say which bots hold how much (`bots: [{botId, size}]`). An account whose positions could not be read is listed under its account id, nothing closed there. The answer is `{"count": 2, "ids": ["hl:ETH", "hl2:BTC"], "refused": []}`; `count: 0` means nothing matched. The Positions list has the same shortcut for you.

### Previewing the request

`POST /api/v1/orders/preview` takes the same body and answers what placing it would answer now, from the same checks with goodcryptoX's own price, balances, position and leverage: `{"errors": [...], "warnings": [...], "receipt": ...}`, each error and warning as `{"key", "text"}` in goodcryptoX's words with every number filled in, and the receipt (side, the size that would be sent, its price, value and what it uses). Nothing is placed or recorded, and any key may ask (the `preview_order` tool). The key's own limits are checked only when it places the order.

### DCA settings from a strategy sheet

The trader walkthrough of the strategy sheet guide uses one entry and four equal averaging orders, 359.35 USDC each, totalling 1,796.75 USDC. These are the corresponding wire fields. Use account and instrument IDs returned by the API; a HIP-3 instrument includes its dex, for example `xyz:MU`.

|---|---|---|
| Market (contract) | `instrumentId` | `ETH`; a HIP-3 market holds its dex: `xyz:MU` |
| Account | `sourceId` | from the agent's list of accounts |
| Signal TA "Buy" (includes Strong Buy), 15m | `entryCondition: "ta"`, `taPeriods: ["15m"]`, `taSignals: ["buy"]` | Buy includes Strong Buy |
| Direct, long only | `entrySide: "direct"` | with only Buy ticked, the bot opens longs only |
| Market entry, no trailing | `entryOrderType: "market"` | |
| Order size in USDC | `sizingMode: "cost"`, `entryAmount` | `359.35` |
| Averaging orders (without the entry) | `avgCount` | `4` |
| First averaging order manual, same size as the entry | `level1Amount` | `359.35` |
| Size multiplier 1.00 | `sizeCostMultiplier` | `1` |
| First step | `level1PricePct` | `0.96` |
| General step | `avgPriceStepPct` | `1.1712` |

| One at a time, Post only off | `averaging: "one"`, `postOnly: false` | |

Every number is sent as text, with a dot: the sheet's `0,96 %` is `"0.96"`. With the example the averaging orders sit 0.960 %, 2.120 %, 3.519 % and 5.200 % below the entry; the sheet's 0.958 %, 2.117 %, 3.517 % and 5.200 % are the same steps rounded to its reference prices, and the preview shows the ladder at the market's price now.

Some strategy-sheet rules have no corresponding DCA setting; report these differences instead of silently substituting:

- Signals of other platforms: goodcryptoX's Signal starts a bot on its own TA rating of 26 indicators, or on RSI, MACD, Bollinger bands or a price move, each with fixed settings (RSI 14 at 30 and 70, MACD 12/26/9, Bollinger 20 closes and two standard deviations). A cross or a re-entry rule of another kind has no setting.
- A modelled loss bound, a full average price or a point of interest: they are the sheet's calculations, not settings. The closest setting, Stop Loss as **Max loss, %**, is a different stop; use it only when the sheet asks for it.
- A breakeven move of the stop-loss, or a time limit counted from the first fill: not settings of the DCA bot (its **Run** limits it to a number of cycles or of days from its start).
- Columns for another platform (its total order count, its stop from the entry): leave them out.

## OpenAPI and reading without the socket

`GET /api/v1/openapi.json` answers the whole API as an OpenAPI 3.1 document, limited to the operations your credential may call: a `read` key sees the reads, a `propose` key also sees what it may propose, you, signed in, see everything. It is generated from the list of routes the server runs and the schemas in `docs/reference/schemas/`, so it cannot differ from either; the copy for everyone is committed as [`docs/reference/openapi.json`](../openapi.json). This page and the document are checked against each other: a route that is in one and not the other fails the build. Operations an AI agent may use carry an `x-gcx-tool` entry; that is how `gcx mcp` builds its tools.

`GET /api/v1/topics/{topic}` is for a program that does not want to open the socket: it answers what the socket's first event for that topic would be (the same `{ledgerId, seq, topic, data}`) and lets go of the topic at once, so a read starts no stream that stays open. A topic that has sent nothing 2 seconds after the request answers **503 "not yet known"**: goodcryptoX does not know yet, which is not the same as "there is nothing", and the program must not read an empty list into it. Try again in a moment. Topic names are those of the socket, below.

## The socket

Open `ws://127.0.0.1:<port>/api/v1/socket` (signed in, or with any access key) and send JSON messages ([panel-socket schema](../schemas/panel-socket.schema.json)):

- `{"op":"subscribe","topic":"orders"}` starts a topic with its snapshot, then sends each change.
- `{"op":"subscribe","topic":"orders","since":{"ledgerId":"…","seq":41}}` after a reconnect sends only what happened after seq 41, when goodcryptoX still holds it; otherwise the snapshot. A `since` from another ledger id (after a backup was restored, or the data folder imported) always gets the snapshot.
- `{"op":"unsubscribe","topic":"orders"}` stops it.

Every event arrives as `{ledgerId, seq, topic, data}`; `seq` never goes back within one ledger id. The panel keeps the last `{ledgerId, seq}` of each topic and, after a dropped connection, subscribes again with it as `since` ([Signing in and staying connected](../../panel/signing-in.md)); a script can do the same. `{"op":"heartbeat"}` arrives every second, so a silent socket is a dead one after 3 seconds. A topic goodcryptoX does not serve, or a message it cannot read, gets `{"op":"refused", …}` and the socket stays open.

Topics: `orders`, `positions`, `bots`, `my-trades` (the take-profit and stop-loss on positions and orders, [schema](../schemas/my-trade-row.schema.json)), `account-state`, `balances`, `dashboard` (the Dashboard's rows, [schema](../schemas/dashboard-topic.schema.json)), `ticks` (every watched instrument's last price; deprecated: use `ticks/<instrumentId>`, below; removed in the release after V1), `leverage/<sourceId>/<instrumentId>`, `candles/<instrumentId>/<resolution>`, and the market data of the trade screen: `book/<instrumentId>/<rung>` (the orderbook at a rung of the exchange's ladder: `finest`, `5m2`, `5m5`, `4`, `3`, `2`; [schema](../schemas/book-frame.schema.json)), `trades/<instrumentId>` (the recent trades as a replay, then each new one; [schema](../schemas/trades-frame.schema.json)), `md-state/<instrumentId>` (how fresh the book and the trades are; [schema](../schemas/md-state-frame.schema.json)), `asset-ctx/<instrumentId>` (mark, index and funding for the price header; [schema](../schemas/asset-ctx-frame.schema.json)), `ticks/<instrumentId>` (the instrument's last price and mark, the last one at once, then each change; it flows while one of the other market-data topics, a bot or a stop holds the instrument, and holds no stream itself; [schema](../schemas/tick-frame.schema.json)). Holding a market-data topic is what keeps its stream from the exchange open: it is released 2 minutes after the last subscriber leaves. With an account connected, `positions`, `balances` ([schema](../schemas/balances-frame.schema.json)), `account-state` and `leverage/<sourceId>/<instrumentId>` ([schema](../schemas/leverage-topic.schema.json)) are kept current while you hold them: `positions`, `balances` and `account-state` live from Hyperliquid's account streams (about every 5 seconds; spot balances when they change), with a read at once, every 60 seconds and within a second of a fill as the backstop; `leverage/<sourceId>/<instrumentId>` is read at once, every minute and within a second of a fill. A reading that fails keeps the last good one and `account-state` says `stale` from its time, or `unavailable` if there was none, never an empty list. Subscriptions made before an account is connected carry on with it.

### Local control status: protection

The owner-only control channel's `status` reply adds optional `protection`: `none`, `passkey`, `passphrase` or `both`. It names the methods that exist without credential data, so the menu shows Reset only for stored protection. Older runtimes omit it; older helpers can ignore it. No HTTP route or stored data changes.

`GET /api/v1/portfolio` adds optional `accounts[].vaults` (total USDC vault equity), `accounts[].led` (of it, the equity in vaults the account leads, which the Dashboard never counts as part of the account; nullable on its own read failure; absent on older runtimes), `accounts[].staked` (HYPE delegated + undelegated + pending withdrawal), both nullable on their own read failures and present even when history returns `error`. The reads (history, vaults, led vaults, staking) run together in the view lane, each reused for five minutes, never on a timer. Optional `pnl.percent` gives nullable day/week/month/allTime time-weighted returns over exactly the successful histories counted by PnL. Paired account-value/PnL instants are merged by time after rebasing each account’s PnL; deposits count from the interval’s start, withdrawals from its end, and the returns are chained. A zero first value is valid; no measurable positive-base interval gives null. The four figures are reused while kept reads and counted membership remain unchanged. Older consumers ignore additions; newer panels accept older answers without them. No stored state changes.

### Account membership in Dashboard results

`POST /api/v1/accounts/{sourceId}/in-portfolio` is person-only (keys receive 403). Send `{ "balances": false }` or `{ "pnl": false }`, or both. At least one boolean is required; only supplied switches are merged for that account. Unknown or removed accounts return 404. The answer is `{sourceId, inPortfolio: {balances, pnl}}`. Identical values write nothing.

`GET /api/v1/accounts` adds `inPortfolio`; absent stored preferences mean both on. `GET /api/v1/portfolio` adds `out: {balances: string[], pnl: string[]}`, live account ids only. PnL amounts, `percent`, `since` and `partial` all count the same included accounts. The history and holding reads remain cached for five minutes regardless of preferences. No journal row, settings field, migration or live push is added. One `meta` row named `in-portfolio` moves with the whole database; restoring an account keeps its id and choice, while a forgotten account added with a new id starts on. Older runtimes omit these fields: newer panels count everything and hide the switches.

The Dashboard frame includes optional `upnlPercent` and `beforeUpnlPercent` decimal strings for Worth figures and actual since-visit movement. Position percent uses admitted margin, bot percent uses Invested; zero/unavailable bases omit the current percent. The previous percent is the value recorded at the earlier visit, never recomputed using today’s base. Older frames/seen records without these fields retain their USDC display. These fields authorize no command and change no ranking formula.

New API/MCP resting orders and TP/SL default to one year (`31536000000` ms) when neither `timeInForce` nor `cancelAt` is supplied, independently of panel Settings. An explicit field overrides. Old journal rows are unchanged.

An API/MCP order's TP/SL, and TP/SL attached to a position or to an order, without `bracket.reduceOnly` are reduce-only, the API's own default, whatever Settings › General › Trading's reduce-only (`bracketReduceOnly`) says; a received `reduceOnly` is honoured. Until this release an order's TP/SL, or TP/SL attached to an order, without it were not reduce-only (TP/SL on a position always were): send `reduceOnly: false` to keep that.

Expiry refusals return 400 with the house reason (always in `error`; at runtime validation also as `{rejected, text}` beside it): an exit Custom deadline lies between the entry's expiry and one year after it (the exits' clock starts at the full fill, at the latest at the entry's expiry), and on a position or an order already filled within one year of acceptance; a TP/SL duration cannot exceed one year. The shared schema and generated MCP tools state the same maximum.

### Moved mode

On a root `moved` marker, normal routes do not run. Signed-in, unverified browsers can read `GET /api/v1/moved` → `{at,file}`, press `POST /api/v1/moved/fresh` → 204, or send the existing octet-stream `POST /api/v1/import`. Every other API path, for a signed-in browser or an access key, returns 409 `{error,moved:{at,file}}` (with no valid credential, 401 as everywhere); socket upgrades return 409. Every panel page path on both canonical names serves `moved.html`; login/icons retain their usual paths. The current browser session hash survives Fresh and accepted moved import. Both actions restart with 75. `status` adds optional `moved`; Open and Stop remain available, other control verbs refuse. These routes exist only in moved mode and are not trading/MCP tools.

Order details may include `parent` (`{kind: "order" | "bot", id}`) and `parentRow`, the canonical order row for a known parent order. Both are optional; a position exit has no order parent. With an older runtime, the panel uses a parent already held in its lists. The existing `children`, `bracket` and `chain` shapes are unchanged.


Grid details additionally return `profitability` buckets, the three investment bases and their APRs. On the first read omit `profitAfter`; pass the returned opaque cursor on later reads to receive replacement values for changed buckets only. Apply `profitabilityRemoved` timestamps before those replacements. Funding is already included in each bucket's `realized`. Invalid or foreign cursors return 400. The bucket contract is [Grid profitability](../schemas/grid-profitability.schema.json).

Key-card statistics accept optional `period=day|week|month|year|all` and native `currency` on `GET /api/v1/keys/{id}`. Unqueried reads retain all-time behavior. Native totals remain present; optional reporting totals retain missing-rate currency IDs. Key activity events carry a stable optional `cursor`. Agent bot details add native filled `volume` buckets; canonical bot profitability remains unchanged.

Key limits accept `accounts: "all"` for every account held now or added later, just as `markets: "all"` covers every market; saved arrays retain their exact scope.
